# Arvectum Tools — Product Principles

These rules are the default product contract for every Arvectum Tools utility.

## 1. One tool, one job, done

Each app solves one clear user problem. New unrelated jobs become separate tools instead of expanding one app into a toolbox.

## 2. Minimum user effort

Optimize the happy path for the fewest meaningful taps. Prefer sensible defaults, automatic detection and system integrations over configuration screens.

## 3. Fast start

Avoid onboarding carousels, mandatory accounts and tutorials unless the platform makes setup genuinely necessary. Explain only what the user must do next.

## 4. Local first

Keep user content on-device whenever the job can be completed locally. A backend must have an explicit product reason.

## 5. Privacy by design

Collect the minimum data required for the feature. Never make analytics, ads or network failures block the core utility.

## 6. System-native behavior

Use platform conventions, system share/save flows, accessibility APIs, Dynamic Type and system Light/Dark appearance unless a product-specific reason justifies otherwise.

## 7. Shared brand, independent product policy

Arvectum Tools share visual DNA and interaction quality. Individual apps may still differ in onboarding, monetization, advertising frequency and feature depth when their usage patterns differ.

## 8. No speculative platform

Do not build reusable frameworks before repetition exists. Duplicate a small amount of code first; extract only after the same stable concept appears in at least two real apps.

## 9. Measurable usefulness

A release is successful when an unknown real user can install the app, complete the intended job and understand the result without assistance.

## 10. Product simplicity beats feature count

When choosing between another feature and a clearer flow, prefer the clearer flow unless evidence shows the missing feature is blocking the core job.
